# 🗄️ ملفات SQL — مرتّبة بترتيب التنفيذ

كل ما تحتاجه قاعدة Supabase في مكان واحد، **مرقّم بحسب الترتيب**.
نفّذ الملفات في **Supabase Dashboard → SQL Editor → New query** (لصق + Run).

| # | الملف | الوظيفة | متى تنفّذه |
|---|-------|---------|-----------|
| **00** | [`00-reset-drop-all.sql`](00-reset-drop-all.sql) | ⚠️ **يحذف كل شيء** (الجداول والرسائل والغرف والدوال ومخطط الأسرار) | فقط إن أردت البدء من الصفر — ثم نفّذ **01** فوراً بعده |
| **01** | [`01-bootstrap.sql`](01-bootstrap.sql) | المخطط الكامل: الجداول + الصلاحيات + RLS + Realtime + دوال RPC + إصلاح الجداول القديمة | مشروع جديد، أو ترقية مشروع قائم، أو بعد تنفيذ 00 |
| **02** | [`02-schema.sql`](02-schema.sql) | **نفس محتوى 01** بترويسة «مخطط» | بديل لـ 01 — لا حاجة لتنفيذهما معاً |
| **03** | [`03-migration.sql`](03-migration.sql) | **نفس محتوى 01** بترويسة «ترقية قاعدة قائمة» (ينقل أسرار النسخ التجريبية) | بديل لـ 01 على مشروع قديم |
| **04** | [`04-repair-messages.sql`](04-repair-messages.sql) | إصلاح سريع لجدول الرسائل: عمود النصّ `body` + عمود المعرّف `id`/التسلسل `messages_id_seq` | عند «تعذّر إرسال الرسالة» أو `relation "public.messages_id_seq" does not exist` — **بلا حذف أي رسالة** |
| **05** | [`05-health-check.sql`](05-health-check.sql) | فحص للقراءة فقط: الجداول، الأعمدة، الصلاحيات، Realtime + إرسال رسالة فحص تُحذف فوراً | بعد أي تنفيذ للتأكد أن كل شيء سليم |
| **06** | [`06-cleanup-cron.sql`](06-cleanup-cron.sql) | تنظيف دوري اختياري (pg_cron): حضور + رسائل + غرف مهجورة | اختياري — الموقع يعمل بلا هذا الملف |
| **07** | [`07-social.sql`](07-social.sql) | ملفات شخصية + صورة Storage + بحث اختياري + صداقة/حظر + مراسلة خاصة وRLS/RPC | بعد 01/02، لتفعيل مساحة الأعضاء 3.0؛ إضافة آمنة دون حذف بيانات |

> ℹ️ **01 و 02 و 03 متطابقة في المتن تماماً** (الفرق في الترويسة فقط). نفّذ **واحداً** منها فقط.
> الملف الأساسي الموصى به هو **01**، وهو آمن للتكرار ولا يحذف أي بيانات.
>
> ⚠️ **00 هو الوحيد الذي يحذف البيانات.** لا تنفّذه إلا إذا كنت تريد البدء من الصفر،
> ثم نفّذ **01** مباشرةً حتى لا يبقى المشروع بلا جداول.

## مساحة الأعضاء الجديدة

لتفعيل `profile.html` و`friends.html` و`messages.html` نفّذ **07 بعد مخطط الغرف القائم**. ينشئ وعاء `wt-avatars` وسياساته أيضًا. [التفاصيل والخصوصية والاختبارات](../social.md).

**لا تنفّذ 00 لهذا الغرض**: ملف إعادة الضبط القديم يحذف دوال `wt_*` الاجتماعية أيضًا وإن بقيت جداولها، وعند استعماله عمدًا يجب إعادة 01 ثم 07. الترقية الجديدة لم تُنفَّذ على مشروعك الحي تلقائيًا.

## وصفات جاهزة (اختر حالتك)

| الحالة | ما تنفّذه بالترتيب |
|--------|--------------------|
| 🆕 **مشروع Supabase جديد** | **01** للغرف، ثم **07** إذا أردت مساحة الأعضاء |
| ♻️ **مشروع قائم فيه غرف/رسائل وتريد ترقيته** | **01** (أو **03**) عند الحاجة لتحديث الغرف؛ **07** لإضافة مساحة الأعضاء — آمن، لا يحذف بيانات |
| 💬 **«تعذّر إرسال الرسالة» (PGRST204 — عمود body)** | **04** |
| 🧨 **`relation "public.messages_id_seq" does not exist`** | **04** |
| 🧹 **جدول قديم تالف ولا تحتاج بياناته** | **00** ثم **01** فوراً |
| ✅ **التأكد أن كل شيء سليم** | **05** |
| 🕒 **تنظيف تلقائي** | **06** (اختياري) |

## الفحص من الطرفية (بدل SQL Editor)

```bash
node tools/sbctl.mjs doctor            # فحص شامل للمشروع الحالي
node tools/sbctl.mjs sql               # طباعة 01-bootstrap.sql
node tools/sbctl.mjs sql --social      # طباعة 07-social.sql، لا ينفذه عن بُعد
node tools/sbctl.mjs sql --repair      # طباعة 04-repair-messages.sql
node tools/sbctl.mjs sql --reset       # طباعة 00-reset-drop-all.sql
node tools/sbctl.mjs sql --health      # طباعة 05-health-check.sql
node tools/sbctl.mjs smoke             # اختبار حي: غرفة + رسالة + حذف
```

## لماذا ملف إصلاح؟ (السبب بلغة واحدة)

مشروع Supabase القديم أُنشئ بنسخة سابقة من المخطط، و`create table if not exists`
**يتجاهل الجدول القائم** فلا يضيف عموداً ناقصاً ولا تسلسلاً مفقوداً. لذلك:

- عمود نصّ الرسالة قد يكون `text`/`message`/`content` بدل `body` → خطأ `PGRST204`.
- عمود المعرّف `id` قد يكون بلا `identity` وبلا `default` → لا يوجد `messages_id_seq`
  → فشل السكربتات وفشل إرسال الرسائل.

الملف **04** (وفي الحقيقة **01** أيضاً) يُصلح الحالتين تلقائياً: يعيد تسمية/يضيف `body`،
ويُنشئ `messages_id_seq` مملوكاً للعمود ويربطه كقيمة افتراضية (أو يعيّن
`gen_random_uuid()` إن كان المعرّف `uuid`/نصّياً)، ثم
`notify pgrst, 'reload schema';` ليقرأ PostgREST المخطط الجديد فوراً.
